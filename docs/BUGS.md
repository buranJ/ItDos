### [P0] 01. Сборка воспроизводимо создаёт админа с общеизвестным паролем

**Файл:** `scripts/seed.ts:207-208`, `scripts/prepare-db.mjs:37-38`, `package.json:7`

**Суть:**
```ts
// scripts/seed.ts:207-208
const email    = (arg("admin-email")    ?? process.env.ADMIN_EMAIL    ?? "admin@itdos.kg").toLowerCase();
const password =  arg("admin-password") ?? process.env.ADMIN_PASSWORD ?? "itdos-admin";
```
`prebuild` (`package.json:7`) на каждой сборке запускает `scripts/prepare-db.mjs`, который при `file:`-базе или пустом `DATABASE_URL` вызывает **`npx tsx scripts/seed.ts` без аргументов** (`prepare-db.mjs:38`). Если `ADMIN_EMAIL`/`ADMIN_PASSWORD` не заданы в окружении — создаётся учётка `admin@itdos.kg` / `itdos-admin`.

Пара логин-пароль вдобавок напечатана открытым текстом в двух местах репозитория: `docs/BACKEND.md:12` и `.env.example:13`.

**Почему баг:** деплой на VPS/Docker с файловой БД (сценарий, прямо рекомендованный в `docs/BACKEND.md:164`) и без явно выставленных `ADMIN_*` даёт рабочий вход в админку с паролем, лежащим в публичной документации проекта. Сид идемпотентен и пропускает существующего пользователя (`seed.ts:220-221`), поэтому смена пароля вручную не откатывается — но первая же сборка на чистом томе создаёт учётку заново.

**Влияние:** полный контроль над контентом сайта и доступ ко всем персональным данным заявок (`/admin/leads` — имена, телефоны, email клиентов). Дефейс, подмена реквизитов, слив базы лидов.

**Предлагаемый фикс:** убрать литеральные дефолты — при отсутствии `ADMIN_EMAIL`/`ADMIN_PASSWORD` завершать сид ошибкой вместо создания учётки. Убрать пароль из `docs/BACKEND.md:12`. В `prepare-db.mjs` вызывать сид контента отдельно от сида пользователя, чтобы CI-сборка вообще не создавала админов.

**Уверенность:** высокая — прочитаны все три файла цепочки.

### [P0] 02. Нет никакого ограничения попыток входа

**Файл:** `src/server/admin/actions.ts:16-24`, `src/server/auth/index.ts:35-56`

**Суть:** `loginAction` не считает неудачные попытки — ни по IP, ни по email, ни глобально. Нет задержки, нет блокировки, нет CAPTCHA. Единственная стоимость попытки — один вызов scrypt.

**Почему баг:** `/admin/login` доступен без cookie (матчер прокси намеренно исключает login — `proxy.ts:27`). Скрипт может слать POST-запросы к Server Function неограниченно. Вместе с BUG-01 (известный пароль) и с тем, что политика паролей отсутствует вообще, это прямой путь к подбору.

Смягчающее: scrypt памяте-жёсткий, так что перебор небесплатен — но от словарной атаки по нескольким сотням популярных паролей это не защищает.

**Влияние:** подбор доступа в админку; параллельно — DoS, потому что каждая попытка занимает CPU на scrypt.

**Предлагаемый фикс:** счётчик неудач в БД (таблица `settings` уже есть, либо новая `login_attempts`) с ключом по email и по IP из заголовка; экспоненциальная задержка после 5 неудач и блокировка на 15 минут после 10. IP брать через `headers()` в экшене.

**Уверенность:** высокая — весь путь логина прочитан целиком.

### [P1] 03. Удаление записи не сбрасывает кэш её страницы

**Файл:** `src/server/admin/actions.ts:64-72` и `:135-149`

**Суть:**
```ts
// actions.ts:64-72
function revalidateFor(resource: ResourceDef, slug?: string): void {
  for (const path of resource.revalidate) {
    if (path.includes(":slug")) {
      if (slug) revalidatePath(path.replace(":slug", slug));   // ← без slug ничего не делает
    } else {
      revalidatePath(path);
    }
  }
}

// actions.ts:135-149
export async function deleteResourceAction(form: FormData): Promise<void> {
  …
  await db.delete(resource.table as never).where(eq(idCol, id as never));
  revalidateFor(resource);          // ← slug НЕ передан
```
`deleteResourceAction` удаляет строку, не прочитав её, поэтому slug ему неизвестен и передать его нечего. В результате из списка `["/", "/portfolio", "/portfolio/:slug"]` (`resources.ts:113`) ревалидируются только первые два.

**Почему баг:** редактор удаляет проект в `/admin/projects` → `/portfolio` обновляется и карточка пропадает, а `/portfolio/<slug>` остаётся в кэше и продолжает отдаваться со статусом 200. Воспроизводится каждый раз при удалении любого `services` / `projects` / `posts` — то есть трёх из восьми типов контента.

**Влияние:** удалённый кейс, услуга или статья остаются публично доступны по прямой ссылке неопределённо долго. Ссылка живёт в поисковой выдаче и в старом `sitemap.xml` (см. BUG-07), так что попадания на неё будут. Для снятого с публикации клиентского кейса это может быть нарушением договорённостей с клиентом.

**Предлагаемый фикс:** в `deleteResourceAction` читать строку перед удалением (`select slug … where id = ?`), передавать slug в `revalidateFor`. Заодно вернуть `{error}` вместо молчаливого `return` на строке 141, когда ресурс или id не найдены.

**Уверенность:** высокая — обе функции прочитаны, поведение `revalidateFor` однозначно.

### [P1] 04. Внешний URL в поле обложки роняет рендер страницы

**Файл:** `src/components/portfolio/ProjectMedia.tsx:45-57`, `src/components/portfolio/ProjectGallery.tsx:21-27,44-49`, `next.config.ts:9-13`

**Суть:** `coverImage` — свободное текстовое поле админки:
```ts
// src/server/admin/resources.ts:132-136
{ name: "coverImage", label: "Обложка (путь к файлу)", type: "text",
  help: "Например /cases/avangard.jpg …" }
```
Валидации нет — `schemaFor` даёт для него `z.string().catch("")` (`resources.ts:337-338`). Значение уходит напрямую в `next/image`:
```tsx
// ProjectMedia.tsx:48-55
<Image src={coverImage} alt={title} fill … />
```
При этом `next.config.ts` задаёт только `images.formats` и **не содержит `remotePatterns`**.

Документация Next 16 из этого же репозитория, `node_modules/next/dist/docs/01-app/03-api-reference/02-components/image.md:71`:
> An absolute external URL (must be configured with `remotePatterns`).

**Почему баг:** редактор вставляет `https://example.com/cover.jpg` (совершенно естественное действие — подсказка говорит про «путь к файлу», но ничего не запрещает) → `next/image` бросает ошибку о неразрешённом хосте. Поскольку `/portfolio/[slug]` и `/portfolio` статические, падение происходит при ревалидации после сохранения либо при следующей сборке.

**Влияние:** страница кейса (или весь список портфолио, где `ProjectMedia` тоже используется) перестаёт рендериться. При этом никакого сообщения в админке нет — сохранение прошло успешно, а сломалось потом и в другом месте. Диагностировать без доступа к логам сборки практически невозможно.

**Предлагаемый фикс:** в `schemaFor` добавить тип поля `imagePath` с проверкой `startsWith("/")`, либо добавить `images.remotePatterns` в `next.config.ts` и разрешить внешние URL осознанно. Минимально — проверять префикс в `saveResourceAction` и возвращать `fieldErrors.coverImage`.

**Уверенность:** высокая — поведение подтверждено документацией Next из `node_modules`, конфиг прочитан.

### [P1] 05. Сообщение об ошибке от сервера выбрасывается в форме заявки

**Файл:** `src/lib/api.ts:30-32`, `src/components/sections/shared/ContactForm.tsx:51-57`

**Суть:** сервер возвращает подробный ответ:
```ts
// src/app/api/contact/route.ts:35-41
return Response.json(
  { success: false, message: Object.values(errors)[0] ?? "Проверьте данные формы", errors },
  { status: 400 }
);
```
Транспорт его игнорирует:
```ts
// src/lib/api.ts:30-32
if (!res.ok) {
  throw new Error(`API error: ${res.status} ${res.statusText}`);   // тело не читается
}
```
Форма ловит `catch` без аргумента и показывает одно и то же на любой сбой:
```tsx
// ContactForm.tsx:55-57
} catch {
  setStatus("error");
}
```

**Почему баг:** клиент и сервер валидируют одной функцией (`lib/validation.ts`), поэтому сегодня расхождение маловероятно. Но оно возникает всегда, когда серверная проверка строже клиентской: любая новая проверка (блок-лист доменов, антиспам, лимит длины), рассинхрон версий бандла у пользователя с открытой вкладкой, или ответ 400 от прокси/WAF.

**Влияние:** посетитель видит «Ошибка отправки. Напишите нам напрямую на …» вместо «Укажите корректный телефон». Он не знает, что чинить, и уходит. Для лид-формы, ради которой существует сайт, это прямая потеря конверсии. Поле `errors` в ответе сервера сейчас не используется вообще.

**Предлагаемый фикс:** в `request()` при `!res.ok` прочитать тело и бросить типизированную ошибку с `message` и `errors`; в `ContactForm` ловить её и раскладывать в `setErrors` + `setStatus`.

**Уверенность:** высокая.

### [P1] 06. Нет ни одного `error.tsx` / `loading.tsx` во всём приложении

**Файл:** `src/app/**` — проверено полное дерево

**Суть:** в проекте отсутствуют `error.tsx`, `global-error.tsx`, `loading.tsx` и вложенные `not-found.tsx`. Единственный обработчик — корневой `src/app/not-found.tsx`, и он покрывает только явный `notFound()`.

**Почему баг:** серверные компоненты ходят в БД без всякой обёртки — `getServices()` (`content/index.ts:37`), `db.select()` в админке (`leads/page.tsx:22`), `db.all()` (`[resource]/page.tsx:28`). Любое исключение (БД недоступна, повреждён файл, истёк `DATABASE_AUTH_TOKEN` у Turso) поднимается до корня.

Сценарий, прямо описанный авторами в `docs/BACKEND.md:183-187`: на Netlify файловая БД в рантайме недостижима. Все четыре страницы админки — `force-dynamic`, то есть читают БД на каждый запрос. Значит на таком деплое `/admin` не просто «не работает», а падает в необработанное исключение.

Отдельно: у страниц с `force-dynamic` нет `loading.tsx`, поэтому во время серверного запроса пользователь видит замерший интерфейс без индикации.

**Влияние:** вместо внятного экрана — дефолтная страница ошибки Next (в проде: «Application error: a server-side exception has occurred»). Ни навигации, ни объяснения, ни кнопки повтора. Ошибка не логируется в приложении.

**Предлагаемый фикс:** добавить `src/app/error.tsx` и `src/app/global-error.tsx` (клиентские, с `reset()`), плюс `src/app/admin/(panel)/error.tsx` с текстом про недоступность БД. Для `force-dynamic` страниц админки — `loading.tsx` со скелетоном.

**Уверенность:** высокая — отсутствие файлов подтверждено полным листингом дерева.

### [P1] 07. `sitemap.xml` не ревалидируется никогда

**Файл:** `src/app/sitemap.ts:26-41`, `src/server/admin/resources.ts:83,113,190`

**Суть:** `sitemap.ts` строит карту из БД:
```ts
// src/app/sitemap.ts:26-34
const [services, projects, posts] = await Promise.all([getServices(), getProjects(), getPosts()]);
const dynamic = [
  ...services.map((s) => `/services/${s.slug}`),
  ...projects.map((p) => `/portfolio/${p.slug}`),
  ...posts.map((b) => `/blog/${b.slug}`),
]…
```
Динамических API не касается → пререндерится на сборке. Но **ни один** список `revalidate` в реестре ресурсов не содержит `/sitemap.xml`:
```ts
revalidate: ["/", "/services", "/services/:slug"]   // resources.ts:83
revalidate: ["/", "/portfolio", "/portfolio/:slug"] // resources.ts:113
revalidate: ["/blog", "/blog/:slug"]                // resources.ts:190
```
Поиск по `src/`: `revalidateTag`, `revalidate =` и упоминаний `sitemap` в путях ревалидации — ноль.

**Почему баг:** воспроизводится при любом добавлении, удалении или переименовании услуги, кейса и статьи. Sitemap застывает в состоянии на момент последней сборки.

**Влияние:** новые страницы не попадают в карту сайта и индексируются медленнее или не индексируются. Удалённые — остаются в карте и генерируют 404 (а с учётом BUG-03 — не 404, а живую страницу-призрак). Для сайта студии разработки, где портфолио и есть основной SEO-актив, это бьёт прямо по цели.

**Дополнительно:** `lastModified: now` (`sitemap.ts:7,21,38`) — это время **сборки**, одинаковое для всех URL. Реальные `updatedAt` в БД есть (`schema.ts:22-24`) и не используются.

**Предлагаемый фикс:** добавить `/sitemap.xml` в `revalidate` для `services`, `projects`, `posts`. Заодно брать `lastModified` из `updatedAt` строки, а не из `new Date()`.

**Уверенность:** высокая.

### [P2] 08. Текст статьи блога выводится как экранированный plain text

**Файл:** `src/app/blog/[slug]/page.tsx:82-85`

**Суть:**
```tsx
<div className="prose prose-gray max-w-none">
  <p className="text-lg …">{post.excerpt}</p>
  {post.content && <div className="mt-8">{post.content}</div>}
</div>
```
Поле `content` объявлено в реестре как `type: "richtext"` (`resources.ts:196`) и отдаётся редактору textarea на 16 строк (`ResourceForm.tsx:90`). Но выводится как обычная строка — React экранирует всё.

**Почему баг:** редактор пишет разметку (Markdown или HTML — тип поля называется «richtext» и других подсказок нет), а на странице она отображается как есть: `<p>Текст</p>` буквально, со скобками. Обёртка `prose` при этом намекает на противоположное.

Класс `prose` вдобавок относится к `@tailwindcss/typography`, которого **нет в зависимостях** (`package.json:30-41`) — то есть он не делает ничего.

**Влияние:** статьи блога нельзя нормально сверстать. Абзацы, списки, заголовки, ссылки невозможны — весь текст одним куском без переносов (даже `white-space: pre-wrap` не задан).

**Хорошая новость:** это же и защищает от XSS. Если будете чинить через `dangerouslySetInnerHTML`, обязательно санитизация; безопаснее — рендер Markdown.

**Предлагаемый фикс:** подключить Markdown-рендерер и `@tailwindcss/typography`, либо — минимально и без зависимостей — разбивать по `\n\n` на абзацы и добавить `whitespace-pre-wrap`. Тогда же переименовать тип поля, чтобы он не обещал больше, чем умеет.

**Уверенность:** высокая.

### [P2] 09. Пустая дата публикации рендерится как «Invalid Date»

**Файл:** `src/lib/utils.ts:16-22`, `src/app/blog/[slug]/page.tsx:71`

**Суть:**
```ts
// src/lib/utils.ts:16-22
export function formatDate(dateString: string, locale = "ru-RU"): string {
  return new Date(dateString).toLocaleDateString(locale, { year: "numeric", month: "long", day: "numeric" });
}
```
Колонка `published_at` имеет `.notNull().default("")` (`schema.ts:148`), поле в админке — свободный `text` с подсказкой «ГГГГ-ММ-ДД» (`resources.ts:207`), схема даёт `z.string().catch("")` (`resources.ts:337`). Формат не проверяется нигде.

**Почему баг:** редактор создаёт статью и не заполняет дату (или пишет «10 августа») → `new Date("")` → `Invalid Date` → `toLocaleDateString` возвращает строку `"Invalid Date"`, которая выводится пользователю.

### [P2] 12. `.catch()` в Zod-схеме молча съедает некорректный ввод

**Файл:** `src/server/admin/resources.ts:313-343`

**Суть:**
```ts
case "number":     shape[f.name] = z.coerce.number().int().catch(0);   break;
case "boolean":    shape[f.name] = z.coerce.boolean().catch(false);    break;
case "stringList": shape[f.name] = z.array(z.string()).catch([]);      break;
case "objectList": shape[f.name] = z.array(z.record(z.string(), z.string())).catch([]); break;
default:           shape[f.name] = f.required ? z.string().trim().min(1, …) : z.string().catch("");
```
`.catch(v)` в Zod — не «значение по умолчанию для отсутствующего поля», а «подставить `v` при **любой** ошибке разбора».

**Почему баг, два разных проявления:**

1. **Потеря данных без уведомления.** Редактор вводит `abc` в поле «Время чтения (мин)» → `z.coerce.number()` не проходит → `.catch(0)` → в БД уходит `0`, форма рапортует «Сохранено». То же для `objectList`: JSON с числовым значением (`{"value": 42}`) не пройдёт `z.record(z.string(), z.string())` и **весь массив** заменится на `[]`. Часовая работа над блоком «Результаты» исчезает, и об этом никто не сообщает.

   Обратите внимание: `readField` уже умеет отдавать ошибку невалидного JSON (`actions.ts:52-57` → `fieldErrors`), но синтаксически корректный JSON неверной формы этот барьер проходит и гасится `.catch([])`.

2. **`""` вместо `NULL` в nullable-колонках.** `accent`, `coverImage`, `client`, `role`, `liveUrl`, `highlight` объявлены nullable (`schema.ts:93,98,105,107,108,95`), но `z.string().catch("")` даёт пустую строку. Дальше маппер проверяет только `null`:
   ```ts
   accent: r.accent ?? undefined,      // content/index.ts:88 — "" проходит как значение
   ```
   Пустая строка доезжает до `style={{ "--m-accent": "" }}` и до `color-mix(in oklab, "" 16%, …)` (`ProjectMedia.tsx:72-74`), что даёт невалидный CSS. Браузер отбросит правило — фатально не будет, но фон отрисуется не так, как задумано.

   Аналогично `{project.liveUrl && …}` (`portfolio/[slug]/page.tsx:100`) — `""` falsy, так что здесь повезло; а вот `project.client ?? project.title` (`:43`) на пустой строке выведет пустого «Клиента» вместо запасного названия.

**Влияние:** тихая потеря отредактированного контента и мелкие визуальные дефекты, которые невозможно связать с причиной.

**Предлагаемый фикс:** заменить `.catch()` на `.default()` там, где нужно значение по умолчанию для пустого ввода, и оставить ошибку валидации там, где ввод действительно некорректен — `saveResourceAction` уже умеет раскладывать `parsed.error.issues` в `fieldErrors` (`actions.ts:99-103`). Для nullable-колонок — `.transform(v => v || null)`.

**Уверенность:** высокая по механизму `.catch()` и по nullable-колонкам; средняя по точному поведению `z.coerce.boolean()` в Zod 4 (не проверял на исполнении).

```tsx
{project.tags.map((tag) => (<span key={tag}>…))}      // portfolio/[slug]/page.tsx:67
{items.map((item) => (<li key={item}>…))}             // :312 — goals/challenges/solutions
```
Эти массивы редактируются в админке как `stringList` (`resources.ts:149,151-154`), а `readField` (`actions.ts:42-47`) убирает только пустые строки — дубликаты проходят.

**Почему баг:** редактор вписывает одинаковый тег или одинаковый пункт целей дважды → одинаковые `key` → предупреждение React и потенциально неверное переиспользование DOM-узлов.

**Влияние:** минимальное для статичного контента; дефект качества и потенциальный источник странных багов при будущей анимации списков.

**Предлагаемый фикс:** `key={`${item}-${i}`}` в местах со строковым ключом. Индексные ключи в декоративных мокапах трогать не обязательно.

**Уверенность:** высокая.

### [P3] 23. Ответ API не валидируется в рантайме

**Файл:** `src/lib/api.ts:34`

**Суть:**
```ts
return res.json() as Promise<T>;
```
`as` — утверждение компилятора, а не проверка. В проекте есть Zod (`package.json:28`), но к ответам API он не применяется.

**Почему сейчас нестрашно:** обе стороны свои, и форма читает из ответа только факт `res.ok` — поля `success`/`message` фактически не используются (`ContactForm.tsx:52`).

**Почему стоит записать:** `.env.example:30-31` прямо предусматривает сценарий «форма уйдёт на отдельный бэкенд» через `NEXT_PUBLIC_API_URL`, а комментарий на `lib/api.ts:1-3` говорит «swap BASE_URL to point at the Python backend». В момент, когда на том конце окажется чужой сервис, `as Promise<T>` начнёт врать.

**Влияние:** сейчас нулевое, потенциально — необнаруженный рассинхрон контрактов.

**Предлагаемый фикс:** при подключении внешнего бэкенда — принимать в `request()` Zod-схему и парсить ответ ею.

**Уверенность:** высокая.

# Что я проверил и НЕ нашёл проблем

Чтобы не создавать ложного впечатления, что аудит пропустил эти пункты:

1. **Секреты в клиентском бандле — чисто.** Все 7 обращений к `process.env` в `src/` перечислены в `ARCHITECTURE.md §0`. Единственная `NEXT_PUBLIC_*` — `NEXT_PUBLIC_API_URL`, и она действительно предназначена браузеру. `DATABASE_URL`, `DATABASE_AUTH_TOKEN`, `TELEGRAM_*` читаются только в `src/server/**` и в route handler'е. Барьер `server-only` расставлен корректно (6 файлов).

2. **`"use client"` не задран вверх по дереву.** Корневой layout серверный; `LenisProvider`, `SiteChrome` и `template.tsx` клиентские, но принимают `children` **пропсом** — дерево страницы остаётся RSC и в гидрацию не утягивается. Это ровно тот паттерн, который здесь нужен, и он применён последовательно.

3. **Ошибок гидрации не нашёл.** `Math.random()` в `src/` отсутствует. `new Date()` при рендере — только `sitemap.ts:7` (не UI). Обращения к `window`/`localStorage` — все внутри `useEffect` либо за `typeof window === "undefined"` (`lib/motion.ts:39`, `lib/gsap.ts:4`, `lib/analytics.ts:27`). `useMediaQuery` использует `useSyncExternalStore` с явным серверным снапшотом (`hooks/useMediaQuery.ts:18`) — правильное решение вместо типичного `useState`+`useEffect`. Модульная переменная `appMounted` в `template.tsx:10` мутируется только в эффекте, поэтому сервер всегда отдаёт `isInitial = true` и первый клиентский рендер совпадает.

4. **`localStorage`/`sessionStorage` не используются нигде** — токенов в браузерном хранилище нет по построению.

5. **SQL-инъекций не нашёл.** Единственный `sql.raw` (`[resource]/page.tsx:26`) получает значение из закрытого union `"position"|"sortOrder"|"publishedAt"` (`resources.ts:58`), не из запроса. Пользовательские значения везде идут через параметризацию Drizzle (`[id]/page.tsx:31`, `actions.ts:116-118`).

6. **Cleanup в эффектах — везде.** Проверил каждый `useEffect` с подпиской: `CustomCursor.tsx:129-139` (7 слушателей + rAF), `Header.tsx:106-111` (rAF + 4 таймера + 2 слушателя), `LenisProvider.tsx:59-63` (ticker + destroy), `FloatingContact.tsx:24-27`, `useInView.ts:34` (`io.disconnect()`), `useMousePosition.ts:21`, `FadeIn.tsx:59` и остальные motion-компоненты (`ctx.revert()`). Утечек подписок, таймеров и rAF не обнаружено.

7. **Бесконечных циклов в эффектах не нашёл.** `useInView` с зависимостью `[inView, rootMargin]` (`hooks/useInView.ts:35`) после установки `inView = true` перезапускается один раз и выходит по guard'у на `:19`. `useMediaQuery` через `useSyncExternalStore` возвращает примитив, поэтому не зацикливается.

8. **Прямых мутаций стейта нет.** Все обновления иммутабельны: `setForm((prev) => ({ ...prev, [name]: value }))` (`ContactForm.tsx:32`), `setActive((a) => …)` (`TeamSlider.tsx:45`).
