# Бэкенд и админка ITDOS

## Быстрый старт

```bash
cp .env.example .env.local
npm run db:migrate      # создаёт data/itdos.db и таблицы
npm run db:seed         # переносит контент из src/data/*.ts + заводит админа
npm run dev
```

Админка — `/admin`. Логин по умолчанию `admin@itdos.kg` / `itdos-admin`.
**Смените пароль до публикации** (значение в `src/lib/site.ts` не при чём —
пароль живёт в БД, задаётся флагами сида).

```bash
npm run db:seed -- --admin-email you@itdos.kg --admin-password 'нормальный-пароль'
```

## Решения по стеку и почему именно так

### Отдельного бэкенд-сервиса нет

Next.js 16 — полноценный сервер: Route Handlers, Server Actions, серверные
компоненты. Отдельный Express/FastAPI рядом дал бы второй деплой, вторую
систему авторизации, CORS, дублирование типов и рассинхрон схем — за нулевую
выгоду на сайте, где пишет три человека раз в неделю.

Граница проведена не по процессам, а по каталогам: всё в `src/server/**`
серверное и помечено `server-only`, поэтому импорт из клиентского
компонента падает на сборке, а не в проде.

### SQLite (libSQL), а не PostgreSQL

Против ожидания — но нагрузка тут читающая и крошечная: контент правят
вручную, страницы статические, запись — десятки в день. SQLite даёт нулевой
ops-оверхед, мгновенные чтения и работает во время `next build`, когда 7
воркеров параллельно пререндерят страницы (Postgres-в-WASM на этом ломается,
он однопроцессный).

`@libsql/client` — тот же SQLite, но с сетевым режимом: одна переменная
`DATABASE_URL` переключает файл на управляемый Turso, кода менять не надо.

**Когда этого перестанет хватать:** несколько одновременных редакторов,
десятки тысяч заявок, аналитика по лидам. Тогда — Postgres. Схема на Drizzle
переносится сменой диалекта в `schema.ts` и `drizzle.config.ts`; запросы в
`src/server/content` и `src/server/admin` останутся как есть.

### Drizzle, а не Prisma

Типы выводятся из схемы без кодогенерации, нет отдельного бинарника движка,
запросы читаются как SQL. Для проекта, где половина работы — это `select …
where published = 1 order by position`, слой Prisma не окупается.

### Авторизация своя, а не Auth.js

Требование ровно одно: несколько сотрудников заходят по почте и паролю.
Auth.js — это OAuth-провайдеры, адаптеры и конфиг, которых тут не нужно.

- Пароль — `scrypt` из стандартной библиотеки Node: memory-hard, без
  нативных зависимостей и без чужого кода в цепочке поставки.
- Сессия — случайный id в httpOnly-cookie, состояние в таблице `sessions`.
  Это осознанно **не** JWT: сессию нужно уметь отзывать, а подписанный токен
  отозвать нельзя.
- Сравнение хешей — `timingSafeEqual`; несуществующий пользователь всё равно
  прогоняется через verify, чтобы по времени ответа нельзя было перебрать
  список почт.

### Две линии защиты

`src/proxy.ts` отбивает запросы без cookie до рендера — но это **не**
авторизация: proxy выполняется раньше приложения и до базы не достаёт, он
видит лишь факт наличия cookie. Настоящая проверка — `requireUser()` в
layout панели и в каждом server action.

## Схема данных

`src/server/db/schema.ts`, 13 таблиц.

| Таблица | Назначение |
|---|---|
| `users`, `sessions` | доступ в админку |
| `services`, `projects`, `posts` | услуги, портфолио, блог |
| `reviews`, `team_members`, `plans` | отзывы, команда, тарифы |
| `faq_items`, `process_phases` | FAQ и этапы работы |
| `leads` | заявки с формы |
| `settings` | key/value на будущее |

**Списки и объекты (features, tags, results, process) лежат JSON-колонками,
а не отдельными таблицами.** Это осознанно: они всегда читаются целиком
вместе с родителем, никогда не фильтруются и не джойнятся. Нормализация
добавила бы join на каждое чтение и diff-согласование на каждое сохранение,
не дав ничего взамен. Всё, что действительно запрашивается отдельно — `slug`,
`category`, `published`, `position` — обычные колонки с индексами.

## Как это связано с сайтом

```
Витрина (RSC)  →  src/server/content  →  Drizzle  →  SQLite
Админка (форма) → server action → Drizzle → revalidatePath() → пересборка страниц
```

`src/server/content/index.ts` возвращает **ровно те же типы**, что
components ждали от `src/data/*`, поэтому переезд был заменой импорта.
Строки маппятся вручную: служебные колонки (`position`, `published`,
timestamps) до React-компонента не доходят.

Кеша поверх запросов нет намеренно: страницы статические, запрос выполняется
на сборке или ревалидации, а не на каждый заход. После сохранения в админке
`saveResourceAction` дёргает `revalidatePath` по списку маршрутов из
`resources.ts` — правка тарифа пересобирает `/`, правка кейса `/portfolio` и
`/portfolio/<slug>`.

`use cache` из Next 16 не включён специально: он требует `cacheComponents:
true`, а это меняет семантику кеширования всего приложения и требует
Suspense-границ вокруг динамики. Отдельная задача, не побочный эффект.

## Админка

Восемь типов контента обслуживает **один** список и **одна** форма.
`src/server/admin/resources.ts` описывает каждый тип полями, а
`/admin/[resource]` и `/admin/[resource]/[id]` рендерят их генерически.
Zod-схема для валидации строится из того же описания.

Добавить новый тип контента = добавить запись в реестр. Отдельный экран
писать не нужно.

Типы полей: `text`, `textarea`, `richtext`, `number`, `boolean`, `select`,
`stringList` (по пункту на строку), `objectList` (JSON-массив).

### Заявки

`/admin/leads`. Заявка **сначала пишется в базу**, потом уходит в Telegram.
Раньше было наоборот — и при упавшей отправке заявка исчезала бесследно.
Ошибка доставки видна в карточке заявки.

## Эксплуатация

```bash
npm run db:generate   # изменили schema.ts → сгенерировать миграцию
npm run db:migrate    # применить
npm run db:seed       # идемпотентно, можно гонять повторно
npm run db:studio     # визуальный просмотр базы
```

**Бэкап** — это копия одного файла:

```bash
sqlite3 data/itdos.db ".backup 'backup-$(date +%F).db'"
```

### Про деплой

- **VPS / Docker** — как есть, файл БД на диске. Нужен постоянный том.
- **Turso** — `DATABASE_URL=libsql://…` + `DATABASE_AUTH_TOKEN`.
- **Vercel и любой serverless** — файловая БД **не подойдёт**: файловая
  система эфемерная и на каждый инстанс своя. Только Turso.

## Что осталось за рамками

- **Загрузка изображений.** Пути к файлам вводятся руками; поля
  `coverImage` / `photo` уже есть. Нужен upload-эндпоинт и хранилище
  (локальный диск для VPS или S3/R2). Отдельная задача.
- **Роли.** Колонка `role` есть (`admin` / `editor`), но правами пока никто
  не ограничен — оба видят всё.
- **Аудит изменений.** Кто и что поменял, не пишется.
- **`clients` и `techStack`** остались в `src/data` — это списки логотипов и
  технологий, не редакторский контент.
